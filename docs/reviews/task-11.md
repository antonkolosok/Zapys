## Ranked findings

1. **P1 — The prepare and destructive cancel actions share an automatic List button row.** `ios/App/RemindersView.swift:31` and `:32` place two buttons inside the same `List` row without independent `.buttonStyle(.borderless)`/`.plain` styling. SwiftUI's automatic List button handling can activate both row actions on a single tap. A user trying to preview a reminder can therefore also enqueue its cancellation, making the preview stale or permanently cancelling the reminder. This is the same concrete interaction pattern addressed in Task 9. Give these buttons independent activation behavior and add a native regression asserting that prepare alone does not cancel, and cancel alone does not prepare/open sharing. Source establishes the unsafe pattern; actual interaction remains UNRUN.

2. **P2 — Re-enabling client reminders cannot restore reminders cancelled automatically by disabling the preference.** `ios/Sources/ZapysCore/SQLiteRepository.swift:132`–`:135` now preserves every matching old state, including `.cancelled`. Disabling reminders saves the client and takes the automatic cancellation path at `:140`–`:142`. Re-enable the same preference before the appointment starts, with unchanged lead/template/channel/recipient: the fresh row has the same content and due time, so it inherits `.cancelled` again. The row remains absent from both the notification window and manual actions indefinitely. The same problem applies when an appointment is cancelled then restored to planned without changing its reminder content. Preserve explicit terminal cancellation on unchanged saves/timezone rebases, but distinguish cancellation caused by lost eligibility from explicit cancellation, and regenerate when eligibility is deliberately restored. Add a real SQLite disable/re-enable regression plus a regression retaining explicit cancellation across unchanged writes. The independent disable/delete test stops before re-enable and does not cover this transition.
